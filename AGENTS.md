# Agent guide

Instructions for an agent working in this repository. Read this before writing
or submitting code.

## Know the repository before writing or committing

You are maintaining `aishell-dsh-plugins` — a set of Cordis plugins for
DeepSeek Harness (DSH). You need its design, its structure and its
implementation in hand before you write or commit code. A change made without
that grounding is the kind that collides with a decision taken earlier for a
reason you could not see.

Design changes here propagate: a shared module's contract is read by several
packages, a bundle's `aggregate.yml` decides what ships, and the plugin API is
defined by an upstream project that breaks between releases.

In practice:

- **Read the documentation under `docs/`** — start with
  `docs/deepseek-harness-0.2.x.md`. Part A is the constraints DSH enforces
  (HMR transactions, fetch routes, settings writes, auth fences); Part B is the
  architecture and authoring manual. If you have not developed a DSH plugin
  before, read Part A first — those are hard rules, and violating one fails at
  load or silently.
- **Read the package you are about to change**, including its `README.md`,
  which states the package's API and extension points.
- **Read what calls what.** `grep` for a symbol before changing its signature;
  the cost of a breaking change is the number of packages that import it.

Do not infer the repository's conventions from another project. This one has
its own build order, its own test seal, and its own commit rules, all below.

## When code conflicts with an earlier decision

**Stop immediately.** If an implementation disagrees with a design recorded in
this repository — a comment stating why something is the way it is, a document,
an existing structure — do not pick one silently, and do not finish the change
first and mention it afterwards.

Say which two statements conflict, quote both, and wait for a decision. The
recorded reason usually exists because the obvious alternative failed once; a
change that ignores it reintroduces the failure without the test that would
catch it.

The same applies to a request that would contradict the repository's rules.
State the conflict; do not quietly comply and do not quietly refuse.

## Correctness: three separate claims

Passing one of these says nothing about the next.

**1. It typechecks.** `pnpm run typecheck` runs both config graphs — `src` and,
per package, `tests` via `tsconfig.test.json`. Vitest transpiles without
checking types, so a suite that runs is not a suite that compiles.

**2. It runs.** Execute the code. Reasoning that the logic is sound is not
evidence that it is: an API returns an unexpected shape, a shell command's exit
code is not what it looks like in a pipe, a library's TypeScript type is
broader than its runtime. Run it and read the output.

**3. It does the job.** A program that runs without error can still be wrong:
a query returns the wrong rows, a renderer draws nothing, a guard passes
everything. Verify the behaviour, not the exit status.

### When you have no way to verify the function

Claim 2 is not a substitute for claim 3. If nothing available can confirm the
behaviour — no test harness, no credentials, no reachable system, no observable
output — **stop immediately and report**. Do not present a change as finished
because it ran without error.

Report three things:

- **What you changed and why** — the design, not a diff summary.
- **What it affects** — which behaviours, which packages, which user-facing
  paths. Name them; "other tools" is not a list.
- **How it should be verified** — the concrete steps or the exact call that
  would confirm it, so the person can run them.

Then wait for a reply. A change that is unverified but described is work in
progress; one that is presented as finished is a defect with a story attached.

## Repository rules

### Build

```sh
pnpm install
pnpm run typecheck    # tsc -b, then each package's tsconfig.test.json
pnpm run test         # vitest run
pnpm run lint         # oxlint
pnpm run build        # tsdown bundles → tsc -b types → aggregate patch
```

`build` runs the bundles **before** `tsc -b` deliberately: tsdown writes `lib/`
with `clean: true`, so running it last would delete the `lib/types/` tree that
`tsc -b` had just produced, and every manifest points there.

A new package must be added to the root `tsconfig.json` `references`, or
`tsc -b` skips it and its types never reach the tarball.

### Generated files

Some files are outputs, not sources. Editing them is editing something the next
build overwrites:

- `packages/aishell-base/cordis.patch.yml` — generated from `aggregate.yml` by
  `scripts/aggregate.mjs`.
- `packages/aishell-base/package.json` — same.
- `packages/*/lib/` — build output.
- `packages/aishell-deploy/src/data/permission-registry.json` — generated by
  `scripts/build-permission-registry.ts`; verify with
  `pnpm run build-permission-registry -- --check`.

### Tests never touch real machine state

`vitest.setup.ts` seals the OS keyring and redirects home-derived credential
paths into a temp directory for every test process. This exists because a suite
in this repository once destroyed a developer's live credentials while green.

Give a test its own keyring through
`__setKeyringModule` from `aishell-dsh-credentials-store`; reach for
`AISHELL_TEST_ALLOW_REAL_MACHINE_STATE=1` only when real storage is the subject.

### Commits

Conventional Commits, enforced by the `commit-msg` hook:
`type(scope): subject` with `type` from `feat|fix|docs|style|refactor|test|chore|build|ci|perf|revert`.

Write the message about why the change is right, not what was edited. No
attribution footers.

### Prose

Code, comments, identifiers, commit messages and documentation are English.
Conversation with the user is Chinese.

A comment explains why the code is the way it is — what it assumes, what would
break without it. It does not narrate what an earlier version did; a reader
should see one design, not a history. Where a fact was measured, say so and
keep the evidence with the claim.
